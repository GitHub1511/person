## 18. The OpenRouter planner and Pi coder loop (`tools/openrouter_helper/`)

This component is a bash helper that repeatedly proposes the next step for the project, delegates its
implementation to a coding agent, verifies the result, and reverts the change if the result impaired the
person.  A complete description is given in `tools/openrouter_helper/README.md`; in summary:

```bash
bash tools/openrouter_helper/helper.sh run     # plan -> Pi codes it -> verify -> rollback on FAIL -> repeat
bash tools/openrouter_helper/helper.sh stop    # from another terminal
bash tools/openrouter_helper/helper.sh status
```

* **Planner.**  The planner reads the newest `out/*.npz` files and JavaScript Object Notation (JSON)
  files, the complexity table, a generated outline of the actual class and function signatures, the git
  state, earlier outcomes, and the number of simulations that the machine can currently execute in
  parallel.  It requests one next step from a free OpenRouter model and writes the result to
  `state/next_task.md`.
* **Gateway** (`proxy.py`, accessible from 127.0.0.1 only).  All requests are routed through the
  gateway.  Models are tried in a fixed order (`inkling-small`, `nemotron-3-super`, `laguna-s-2.1`,
  `nemotron-3-ultra`, `ling-3.1-flash`), subject to limits of 200 requests per model per Coordinated
  Universal Time (UTC) day, 20 per minute and 1000 per day; these limits are persisted across restarts.
  Tool calls are passed through and replies are streamed, so that an agent can use the gateway.  A live
  probe showed that `ling-3.1-flash` is no longer free (it is skipped), that `inkling-small` is served
  only to coding agents (Pi identifies itself accurately and is accepted), and that `nemotron-3-ultra`
  is intermittently overloaded.
* **Coder.**  [Pi](https://pi.dev) is run with an isolated configuration directory, with the gateway as
  its only model, with **no application programming interface (API) key in its environment**, with a
  tool-call budget and a time limit, and with `pi_agent/extensions/guard.ts`, which blocks (and logs to
  `state/pi_audit.jsonl`) `git push`, package installations, recursive deletions, system or security
  changes, web requests that send data, secrets, and writes outside the project or into the helper.  The
  guard matches commands by pattern: it is a tripwire and **not a sandbox**.
* **Verification.**  A snapshot is taken before each plan.  After the coder has run, the following
  conditions are checked: the changed files must compile; the package must import at `base` and `rich`; a
  20 s smoke simulation must run without not-a-number (NaN) values or a fall and must not be >25 %
  slower; and the helper and the key must remain untouched.  On FAIL the files are rolled back.  The
  tests, all of which run offline on throwaway copies, are `tests/test_gateway.py`,
  `test_safety_net.py`, `test_run_loop.py` and `test_pi_coder.py`.

**What verification does not check.**  Verification establishes that the simulation still runs, not that
the acceptance criteria of the step were met.  A step can consequently be "accepted" while performing its
task poorly.  The first live step (below) illustrates this.

### 18.1 Outcomes of the first two live steps (2026-10-07)

The loop was run twice and was then stopped deliberately so that the README could be written.  Both
steps were **accepted by verification** (smoke run: 1.87 ms/step after step 1 and 1.74 ms/step after
step 2, no fall, no NaN values, imports at `base` and `rich`).  Both addressed the same area, olfaction
and taste (constant zero in the run files), using `inkling-small` through Pi (about 67 and 59 gateway
requests, and about 5 and 6 minutes, respectively).  The guard blocked nothing: no step attempted a
forbidden command.

**Step 1** (task: to make olfaction and taste vary with internal state and respiration, behind a
complexity flag, with a validation script).  Pi added `World.get_odorant_concentration` /
`get_tastant_concentration`, which return a constant 0.02 above z = 0.1 m and a constant 0.01 inside a
small box at a fixed point; the receptor output was overwritten with these values, and small appraisal
and hunger/thirst adjustments were added, together with unused variables and duplicated code, in
`agent.py`.  Nothing depends on hunger, blood chemistry or respiration; there is no flag, no
`tools/validate_olfgust.py`, and no correlation with internal variables.

**Step 2** (task: stimulus sources coupled to body position).  Pi added `embodied_human/stimuli.py` (an
odour source at (1, 0, 0.5) and a taste source at (-1, 0, 0.5), with concentration ~ 1/distance), a
`stimuli` flag in `complexity.py`, `World.get_odorant_at` / `get_tastant_at`, and two small visible
spheres in the scene when the flag is on, and **rewrote `ChemoSystem.sense`**.

The deficiencies of the result are listed below; they were identified from the diff and the code, and not
all of this was verified by execution:

* **A regression at every level.**  The original olfaction of scene objects (distance falloff, receptor
  adaptation, a novelty signal) and the gustation that occurred when the tongue contacted an object were
  **deleted** from `ChemoSystem.sense`, which now reads only the two fixed sources.  In the absence of
  sources (every level except `rich`), the olfactory and gustatory channels are exactly zero;
  consequently, objects in the scene no longer produce any olfactory or gustatory signal.
* **The flag is enabled only for `rich`.**  The default level (`extreme`) and `max` have
  `stimuli=False`; at the default level the sensory channels are therefore zero again.
* **Two overlapping implementations**, originating from steps 1 and 2 (the constant boxes and the
  1/distance sources), both remain in the code, together with residual unused variables.
* The channels still do not depend on hunger, blood chemistry or respiration, which was the actual
  objective.  Pi's own measurement yielded a standard deviation of ~0.003 over near-body points at
  `rich`.
* The README section written by Pi stated "inversely proportional to squared distance", whereas the code
  implements 1/distance.  The corresponding text was removed from this file.

Verdict: **accepted by verification, but not acceptable as work.**  Verification cannot detect this
kind of damage, because the smoke run never exercises olfaction or taste.  `git log` records the changes
as `autosave:` commits from about 08:28 to 08:41 on 2026-10-07; `git diff 9bdca1b HEAD -- embodied_human`
yields both steps combined (9bdca1b is the last commit before step 1).  **Both steps were reverted** at
the request of the owner: the eight edited files under `embodied_human/` were restored to their state
before step 1 and the new `stimuli.py` was removed.

A known defect of the helper: `state/history.jsonl` records the step title as "?" (the title is read
through a path that Python on Windows cannot open).  The defect has not yet been corrected, because the
script was running.

### 18.2 Considerations before leaving the loop running

* The loop consumes the free daily quota autonomously; one coder step costs tens of requests, so that on
  the order of 10-30 steps a day can be expected.
* Free models produce weaker code than a careful author would; the changes that the loop makes should be
  reviewed.  `state/history.jsonl` lists each step and its verdict, and `state/pi_audit.jsonl` lists
  every tool call.
* The OpenRouter key was pasted into a chat during set-up; it should be rotated.
